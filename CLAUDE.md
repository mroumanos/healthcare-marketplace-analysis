# Marketplace Data Scraper — Claude Context

## Purpose
This folder is a small research workspace for collecting publicly available U.S. health-insurance Marketplace information across states. Marketplace operations vary by state. Some states use the federal HealthCare.gov enrollment platform; others operate a separate state platform. The workflow is three notebooks over the `scrapers/` package: pull (`run_scrapers.ipynb`), compile (`compile_csvs.ipynb`), analyze (`analysis.ipynb`). Keep code and configuration small and easy to read.

## Current scope and assumptions
- Targets are states whose consumer-facing Marketplace flow uses HealthCare.gov for 2026 coverage (including SBE-FP states), plus state platforms that have their own module (Virginia; Maryland is blocked, see below). Confirm a state's Marketplace model against current official sources before each coverage year; Oregon says its residents will use ExploreHealthOR.gov for 2027 coverage.
- The seed URL registry (`marketplace_urls.csv`), the single-page starter notebook and `data/state_csvs/` were removed on 2026-11-18; the plan-quote scrapers replaced them.

## Files and data layout
- Keep raw observations distinct from normalized/derived analysis. Do not silently overwrite prior data if a later run needs to preserve a history; decide on append/versioning before scaling up.

- `scrapers/`: one package per site, each requesting and logging raw responses and providing a parser for them (no CSV column mapping in the package, by user decision 2026-11-18; `fetch_plans` returns the site's plan objects unchanged). Each package holds `scraper.py` (the `Scraper` subclass), `parser.py` (`iter_plans(response, url)`: yields each plan object in one of that site's responses; registered in `PARSERS`, with `scrapers.iter_raw(path)` and `scrapers.iter_plans(entry)` as the entry points) and `settings.py` (its defaults: endpoints, page size, as a pydantic-settings class overridable by `MARKETPLACE_<MODULE>_<FIELD>` environment variables or a `.env` file). `federal/` posts to the HealthCare.gov plan-search API, which rejects a request without a county FIPS; `state/virginia/` drives the three-step flow on enroll.marketplace.virginia.gov, one cookie jar per scenario; `state/maryland/` posts the single pre-eligibility form on app.marylandhealthconnection.gov (single-member households only; request layout from a browser capture). Shared code stays at the top level: `scenarios.py` builds site-independent scenarios (ZIP × age × dependents × spouse × gender × income), `settings.py` has the `ModuleSettings` base, and `config.py` has the validated models for `marketplaces.json`. Add a state platform as `state/<name>/` and register its scraper in `MODULES` and its parser in `PARSERS` in `scrapers/__init__.py`.
- `marketplaces.json`: HTTP politeness settings (including `http.max_concurrency`, requests in flight per module, default 1), and the `scenario` grid (`zip_codes`: `"*"` for every residential ZIP of the state, one ZIP, or a list; `ages`; `num_dependents`; `spouse`; `genders`; `fpl_multipliers`). Unknown keys are rejected. The states to run are not in this file: `run_scrapers.ipynb` has a `STATES` dict (`{"AK": {"module": "federal"}}`, optionally with `"overrides"` for that module's settings and a run id `"suffix"`) passed to `load_config(path, states=STATES)`, which validates it; a `states` block in the file is only a fallback. The registered modules are `federal`, `virginia` and `maryland`. Quotes are collected per county, not per ZIP (user decision 2026-11-18): HealthCare.gov responses were byte-identical for every ZIP of a county in the Alabama and partial Arkansas runs, and a per-county Hawaii run reproduced the per-ZIP result for all 67 ZIPs. Every scraper has `resolve(location, coverage_year)` (ZIP -> its in-state counties; federal uses the site's `/counties/by/zip/{zip}`, the default is `resolve_local` from `zipcodes` + `addfips`, which knows one county per ZIP). The scrapers do not use rating areas. Not checked: states where an insurer serves only part of a county.
- Maryland's Akamai edge returned 403 "Access Denied" to this client for every request, including the public home page (2026-09-30). The client keeps its descriptive User-Agent and does not imitate a browser; do not add browser spoofing or replay browser cookies to get past it.
- `run_scrapers.ipynb`: the run coordinator (pulls the data). Its second code cell resolves every ZIP of each state to counties, saved and reused as `data/reference/zip_counties/<ST>.csv` (one row per ZIP-county pair, with source and retrieval time), prints ZIPs -> counties per state, and sets `generator.counties` (one `Location` per county, carrying the first ZIP found in it). `run_county` quotes every household for one county; `run(state)` works through a state's counties `max_concurrency` at a time. States in `STATES` run one after another, one run per state, with run id `<timestamp>_<suffix>` from `scrapers.state_run_id` (suffix defaults to the state code). Each run writes to the config's `output_dir` (currently `data/results`): `<run_id>.raw.jsonl` (one line per response: `run_id`, `retrieved_at_utc`, `source`, `url`, `scenario`, `request`, `response`) and `<run_id>.config.json` (the config used, plus the module settings each state resolved to). Runs never overwrite each other.
- `compile_csvs.ipynb`: turns raw files into `data/csv/<run_id>/<county_fips>.csv`, one file per county (dask bag parses the JSONL blocks in parallel, rows are then grouped in pandas), so `dd.read_csv("data/csv/*/*.csv")` loads everything with one partition per county. The CSV row format lives in the notebook, not in `scrapers/`: `scenario_columns` (shared provenance/household columns) plus one `<site>_rows` function per module, registered in `ROWS`; each loops over `scrapers.iter_plans(entry)` and maps a plan to columns. Federal rows are verified against earlier output; the Virginia and Maryland functions are ports that have not been run on data.
- `analysis.ipynb`: county-level by default (user decision 2026-11-18): aggregates the compiled CSVs to one value per county (config cell: `METRIC`, `STAT`, `FILTERS`) and draws an ipyleaflet choropleth on TIGER county boundaries with state outlines; TIGER files download into `data/tiger/` when first needed. Its last section is an optional alternative that maps the county values back to ZIPs via `data/reference/zip_counties/` and ZCTA polygons (ZCTAs approximate ZIPs; PO-box ZIPs have no polygon). When reading TIGER files with a pyogrio `where` filter, the filter column must be among the columns read or no rows come back.
- `README.md`, `requirements.txt`, `.gitignore`: for the GitHub repo. Everything under `data/` is ignored: `data/results/` (runs), `data/runs/` (older runs), `data/csv/` (compiled), `data/tiger/` (TIGER 2025 shapefiles, one `tl_2025_us_<state|county|zcta520>/` folder each) and `data/reference/`.
- `scraper.ipynb` and `premium_map.ipynb` were removed on 2026-11-18 (superseded by the modules and by `analysis.ipynb`).
- `rating_areas.ipynb`: one polygon per ACA geographic rating area per state, with the counties, ZIP prefixes, and ZCTAs inside it (`zips` = at least 1% of the ZCTA inside, `zips_no_overlap` = at least 99%). Definitions are scraped once from the CMS state-gra pages into `data/reference/cms_gra/`; polygons use the county and ZCTA shapefiles in `data/tiger/`, and are validated against the state polygons there. Output: `data/reference/rating_areas.parquet` (GeoParquet, list columns) plus a CSV, cached per state under `data/reference/rating_areas/`. The notebook also validates coverage (`data/reference/rating_area_coverage.csv`) and exports `data/reference/rating_area_zips.json`. It is reference material only: the scrapers no longer read it (removed 2026-11-16). The notebook ends with an ipyleaflet inspector (`build_state_map`) that overlays a state's rating areas, counties, and intersecting ZCTAs as three toggleable layers, with ZCTAs coloured by how cleanly they sit in one area.

## Scraping and data-quality requirements
1. Use official Marketplace/state sources and public, non-authenticated pages or explicitly published datasets/APIs.
2. Before adding a target or increasing crawl scope, check the source's terms, robots policy, and applicable usage restrictions. Identify the source, retrieval time, coverage year, and parsing method in the output.
3. Be polite: send a descriptive User-Agent, set timeouts, keep concurrency low, cache responses where practical, and do not repeatedly request the same page. Add backoff before any multi-page iteration.
4. Do not bypass authentication, access controls, CAPTCHAs, or anti-bot measures. Do not collect consumer application data, credentials, health details, or other personally identifiable/sensitive information.
5. Treat HTML as unstable. Keep selectors and parsing logic explicit and site-specific; validate expected fields and surface empty/unexpected results rather than implying success.
6. Record source URL, retrieval timestamp in UTC, state/abbreviation, and coverage year for each saved record. Preserve units and source labels for any future prices or plan attributes.
7. Never interpret scraped material as personalized insurance advice or eligibility guidance.

## Notebook conventions
- Site-specific request and parsing logic lives in `scrapers/`, not in notebooks. Each notebook starts with a short configuration cell of plain constants; pulling, compiling and analysis stay in their own notebooks.
- Keep parsing and writing functions small so state-specific page variants can be added without mixing collection and analysis.
- Do not add a browser automation dependency unless a documented, permitted public source requires it and the user approves that expansion.
